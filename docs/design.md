# CheckMates 产品与技术设计（MVP v1）

状态：**已确认；按用户要求将真实 OCR 纳入本次 MVP**
日期：2026-09-26
范围：移动端优先的餐厅小票分账网页；本文件用于确认设计，下一步再开发。

## 1. 产品目标

CheckMates 帮朋友在聚餐、周末出游和旅行吃饭后，快速算清每个人应付多少。理想体验是：拿出手机，确认小票，点选谁吃了什么，看到一份可以复制分享的结果。网页无需登录；当前账单保存在本机浏览器中。

第一版必须包含**真实的浏览器端 Tesseract.js OCR**。拍照或上传后，实际读取该图片中的文字，提取候选项目与金额，再由用户核对后分账。示例账单作为独立的体验入口保留；上传图片识别失败时提供重试或手动录入，不能填入示例明细冒充识别结果。

成功标准：用户可以上传一张真实英文餐厅小票，看到由该图片识别出的明细，修正遗漏或误读后完成分账，分享准确结果，刷新后继续当前账单，并重新开始。每个人的金额加总必须与确认后的账单总额完全一致。

## 2. 体验与页面结构

整个产品是一页内的五步向导，不为每一步建立独立路由。手机上主要内容保持在舒适的窄列中，宽屏时居中展示，底部固定当前步骤的主要操作。

| 步骤 | 用户看到什么 | 主要操作 |
| --- | --- | --- |
| 1. 开始与识别 | 品牌标题、拍照/上传、示例入口；选图后显示准备图片、加载识别资源和识别文字的进度 | 选择照片、取消识别、失败重试或手动录入 |
| 2. 核对小票 | 原图、识别的候选明细、税、小费、原票合计与计算合计；标出不确定项和差额 | 修改、补齐、删除项目；核对金额 |
| 3. 加入朋友 | 彩色姓名标签、添加姓名输入框 | 添加、改名、删除参与者 |
| 4. 分配菜品 | 每道项目下显示全部朋友，已选择者高亮；支持多人共享和“全员分享” | 为每道项目选择至少一人 |
| 5. 查看结果 | 每人应付金额、项目/税/小费明细、账单总额 | 复制文字结果、返回修改、重新开始 |

步骤标题使用亲切、直接的语气，例如 “Check the receipt”、“Who's in?”、“Who had what?”、“All split!”。金额和错误提示保持清楚严谨。结果页写“分账完成”，不暗示付款已经发生。

用户可以返回前一步修改。离开分配步骤再回来时，已有选择保留；删除参与者会同时从所有项目的选择中移除。重新开始会清除当前账单和本地缓存，回到首页。

## 3. 视觉方向

选择**周末小餐馆**作为第一版的主视觉：温暖、轻松、有一点手帐和纸张质感。出游氛围通过短文案和少量贴纸元素表达，避免装饰干扰分账。

- 背景：温暖奶油白；主操作色：番茄橙；辅助色：薄荷绿、淡黄、柔和紫，用于朋友标签和局部强调。
- 核对区域：小票纸张、虚线分隔、清楚的金额对齐。其他内容用大圆角和轻阴影，留足触控间距。
- 字体：易读的无衬线正文；标题可以更活泼，但金额始终使用稳定、易比较的数字样式。
- 图形：Lucide 图标搭配少量食物、杯子、旅行路线等简单装饰。不把 emoji 当成唯一信息标记。
- 动效：步骤切换和选中标签有轻微反馈；支持系统减少动画设置。

移动端优先设计以约 375px 宽的手机为基准。交互目标至少 44px 高；输入框、金额和错误提示在窄屏上也应完整可读。颜色区分朋友时，同时显示姓名，避免只靠颜色传达信息。

## 4. 金额与分摊规则

所有业务金额都以**整数分**存储和计算；输入框接受美元金额文本，确认时转换成分。第一版界面使用 USD。小票项目价格表示该行总价；不单独处理数量和折扣。小计由项目相加得出，总额由小计、税和小费相加得出，不能直接修改总额。

1. 某项目只分给一人时，该人承担整行价格。
2. 某项目由多人共享时，按人数均分到分；多出的分按参与者的稳定顺序依次分配。
3. 汇总每个人的税前项目金额后，税和小费**分别**按该金额占小计的比例分摊。
4. 比例分摊使用最大余数法：先取每人的整数分，再按余数从大到小分配剩余的分；余数相同按参与者稳定顺序处理。
5. 结果必须满足：每个人的项目金额之和等于小计；税之和等于税总额；小费之和等于小费总额；每个人应付金额之和等于账单总额。

进入结果页前至少有一个人、一个有效项目，且每个项目都分配给至少一人。金额不得为负数或超过两位小数。如果小计为零但税或小费大于零，提示用户调整账单，暂不计算。错误应指出具体项目或字段，保留用户已输入的内容。

## 5. 数据与技术边界

使用 Next.js App Router、TypeScript、Tailwind CSS、shadcn/ui、Zustand 和 Lucide。首页路由只有 `app/page.tsx`；向导步骤是同页组件。UI 读取和更新 Zustand 中的当前账单；`lib/money` 负责金额解析/展示，`lib/split` 只接受账单数据并返回结果，不读取浏览器或修改输入数据。

建议的职责分布：

- `types/bill.ts`：项目、参与者、账单、步骤与分摊结果的类型。
- `lib/receipt.ts`：独立示例账单；真实图片不会走此示例入口。
- `lib/ocr/client.ts`：浏览器 OCR worker 的加载、进度、取消、错误和资源释放。
- `lib/ocr/preprocess.ts`：图片解码、方向调整和有尺寸上限的预处理。
- `lib/ocr/parseReceipt.ts`：将识别文字解析成可编辑草稿，保留未识别金额、原始行和警告。
- `lib/money.ts`：金额文本与整数分的转换。
- `lib/split.ts`：纯计算函数与确定性舍入。
- `store/useBillStore.ts`：向导状态、账单编辑、本地持久化与重置。
- `components/home`、`receipt`、`people`、`split`、`result`：每一步的界面。

本地缓存保存步骤、项目、参与者、税、小费、上传文件名，以及尚未确认的识别草稿和警告。照片本身不写入 localStorage，以免大图占满浏览器额度；刷新后仍能继续核对草稿或编辑账单，但需要重新选择照片才能查看原图。识别中的 worker 和进度不恢复，刷新后提示重新选择图片再识别。界面会明确说明这一点。缓存版本变化时，应安全回退到新账单，避免旧数据导致页面无法打开。

## 6. 本次 MVP 的真实 OCR

识别范围先覆盖清晰、印刷体的英文餐厅小票，USD 金额，JPEG、PNG、WebP 图片。超出支持范围的格式（如未能解码的 HEIC、PDF）明确提示更换格式；不声称已支持多语言、手写小费或所有票据排版。

图片在浏览器内处理，按需加载 Tesseract.js 并使用单个 worker。worker、WASM 和英文模型资源配置版本和加载路径；首次使用需要加载识别资源，加载失败时可重试或手动填写。准备、识别和解析各阶段给出真实状态；取消、超时、重选、重置后停止旧任务，其结果不得覆盖新的账单。部署资源路径必须在生产构建中验证。依据：[Tesseract.js API](https://github.com/naptha/tesseract.js/blob/master/docs/api.md)、[资源部署说明](https://github.com/naptha/tesseract.js/blob/master/docs/local-installation.md)。

解析时提取项目名称与行总价，区分 subtotal、tax、total、实收 tip/gratuity 与建议小费；建议小费不自动入账。保留小票上的原始小计和总额用来核对，不把它们当菜品。无法确定的价格保持待填写，不默认为零；复杂数量、折扣、服务费或重复合计产生核对提示，让用户修正行总价或确认费用归类。

已明确列出的实际小费导入小费字段；没有实际小费时默认 0，由用户追加。缺失的税额要求用户填写或明确确认为 0。原票总额与计算合计有差异时展示差额，用户必须修正或显式确认差异原因（例如另加小费）后才能继续。识别失败或没有可用项目时保留原图、原始文字和手动录入入口。

OCR 只生成待核对草稿。计算函数只接收用户确认后的有效整数分账单，避免识别疑点直接变成分摊金额。

第一版不包含账号、云端同步、支付、多张小票合并或自动识别菜品归属。

## 7. 开发验收

- 从示例入口和真实照片入口都能走完五步；照片路径实际执行 OCR，结果来自所选图片，不能由固定文本或示例数据代替。
- 真实浏览器中运行真实 Tesseract worker，验收清晰英文小票的项目/金额、税和总额提取，并测试空白、模糊、旋转、取消、重试和资源加载失败。
- 使用可合法用于测试的小票照片记录提取结果和需人工修正的地方；生成的测试小票与实拍照片分别标明来源，不把自动化 fixture 通过当作所有实拍场景准确率保证。
- 低把握字段、缺失金额、建议小费和合计不匹配都能被发现并修正；原票合计与分摊总额的比较不能因重复计算小费而失真。
- 编辑项目、税、小费、参与者和归属后，结果立即反映修改；未分配项目不能进入结果页。
- 多人共享、奇数分金额、比例税/小费及余数相同的情况有自动化测试，所有合计精确对账。
- 复制的结果包含每人应付金额和账单总额；重置后旧账单不再出现。
- 刷新页面恢复当前账单；手机窄屏可以完成全部操作；键盘可使用主要控件。
- 开发完成时 `lint`、测试和生产构建通过，README 写清启动方式、架构、OCR 资源部署、支持范围、实际验证记录与已知限制。

## 8. 已确认的默认方案

用户已 review 并接受本设计，按草案的默认方案执行：

1. 主视觉采用“周末小餐馆”。
2. 第一版使用英文界面，金额使用 USD。
3. 无实际小费时默认为 0；真实小票上明确列出的已加小费导入后供用户核对，建议小费不自动计入。
4. 真实 OCR 是本次 MVP 的必要交付，不延后到下一阶段。
