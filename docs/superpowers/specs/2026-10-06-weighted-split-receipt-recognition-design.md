## 目标与范围

用户希望：① 一份菜由多人按实际吃的数量或比例承担费用，例如 6 个鸡翅，四个人吃 `2 / 2 / 1 / 1`；② 利用提供的三张真实小票改善识别；③ 先 review 计划，再开始开发。

建议默认：保留当前均分体验；每道菜可切换均分、比例、按数量；继续浏览器本地 OCR、英文界面、USD 和人工确认。按数量首版只接受整数单位，比例接受正整数权重（如 `2:2:1:1` 或 `50:25:25`）。半份可用比例表达。这里的规则均为本次 review 的建议，并非已经获批的产品行为。

不纳入本次：支付、多人同步、云端 OCR、自动猜测实际食用数量、完整套餐定价、全单优惠分摊、按税种重新分配税费、中文 OCR 模型。超市英文商品行仍属于本次识别范围。

## A. 按菜品分配

### 数据与计算

用单一 `allocation` 替换 confirmed item 的顶层 `personIds`，避免选中成员与权重两套真值不同步：

```ts
type ItemAllocation =
  | { mode: "equal"; personIds: string[] }
  | { mode: "ratio"; shares: { personId: string; units: number }[] }
  | { mode: "quantity"; totalUnits: number; unitLabel: string;
      shares: { personId: string; units: number }[] };
```

canonical shares 只保存正整数 units；输入 0 表示不参与，保存时移除该 share。金额仍是非负安全整数分；units / totalUnits 必须是安全整数，totalUnits > 0。重复或未知 ID、负数、非整数与溢出均拒绝。未分配和数量尚未分完可作为编辑中的 bill 保存，但不可进入 Result。全零账单仍支持；非零税/小费与零小计仍拒绝。

`allocateItemCents(item, people)` 是逐菜唯一计算入口，按稳定 `bill.people` 顺序把权重传给现有 `allocateCents`；预览、结果与复制使用同一计算结果。把 allocateCents 原实现移到独立 `src/lib/allocation.ts`，split.ts 保留兼容导出，避免 split 与 item-allocation 相互导入。只有数量模式要求 sum(units) === totalUnits；比例模式直接归一化。份数不是美元金额，不先算四舍五入的“单个鸡翅价格”。

**三个概念分离：** receiptQuantity 是购买的份数；totalUnits 是用户设定的可分配单位数；units 是某人实际承担的数量/权重。一份小票菜不自动等于一个鸡翅；OCR 数量只作为可选择的建议，用户明确设置 totalUnits。

税、小费保持当前按个人菜品小计分配的总池规则。税码先记录用于核对，本次不根据税码改变个人税费算法；需要按商品税组分配时另行设计。

### 操作体验

- 默认 `Equal`，现有成员 chip / Everyone 操作继续可用。
- `Ratio` 为各成员输入整数权重，显示如 `2/6 · $4.00`。
- `Quantity` 输入总数、单位标签和每人数量；显示 `Assigned 5 of 6 pieces`，不足或超出不能查看最终结果。
- 两种自定义模式都提供即时有效预览；无效输入展示原因，不显示旧金额冒充新金额。
- $12 的 6 个鸡翅分为 `2/2/1/1` → `$4/$4/$2/$2`；$10.01 同比例 → `$3.34/$3.33/$1.67/$1.67`。最大余数补分由稳定成员顺序打破余数相同的平局。
- 切回均分明确提示自定义份额将重置；只重置当前菜。删除成员移除相关份额，数量模式剩余未分配显式提醒，不偷偷归一化。
- 未完成的输入另存字符串型 `allocationEdits`，例如空白 totalUnits；点击 `Apply shares` 后才更新 canonical allocation。待应用编辑阻止进入 Result，刷新后可继续编辑。

### 恢复与兼容

session 版本升至 2；v1 的每个 item / ReceiptEdit.item 的 personIds 迁移为 equal allocation，已有姓名、金额、草稿、步骤与未完成文字保留。v2 正常恢复；未知版本/损坏数据维持现有安全恢复路径。迁移不重新 OCR，不重新分配，不保存派生结果。结构校验允许未完成分配；进入 Result 的业务校验才要求份额完整，不能因还没分完而丢弃整个 session。

## B. 小票识别流水线

`照片校正 → 本地 OCR（text + blocks）→ 行/词坐标 → 行分类与关联 → 金额候选校验 → 可编辑草稿 → 人工确认 → Bill`

1. **图像层：** 保留现有四角裁切、透视与旋转；以真实样本比较正文/金额列是否更完整。木纹、邻票、手遮挡是需要提示的质量信号。增强扫描最多增加一次候选识别，整个任务共享现有 120 秒预算与 AbortSignal；失败仍可手动输入。
2. **OCR 层：** 已安装引擎类型支持 `blocks`，显式开启并在 worker 边界转成 `OcrLine { text, confidence, bbox, words }`；无 blocks 时回退文本解析。仅保存必要的行证据与坐标，不把完整 symbol/候选字体等大对象塞进 session。
3. **分类层：** 区分 charged item、modifier/included、unit-price/promotion、discount、subtotal、item-count、tax、grand-total、payment、metadata、unknown。组合位置、缩进、关键词和数字格式，先识别具体 label 再匹配泛化 total；付款区和底部税表独立分段。不能全局过滤 `table` / `order` / `chicken` 而丢失收费项。
4. **关联层：** 同一收费行保留数量、菜单编号候选、单价与整行价；多行菜名按版面关联。明确收费加料独立列出，可记录 parent；included 项附在主菜下但保留源行；不确定的无价菜仍为待复核收费候选。
5. **折扣层：** 把折扣幅度作为非负 discountCents 元信息，归属明确时关联商品。检测 `already included / subtract / unresolved` 三种语义；用明确单价关系与全单等式提供证据，不凭相邻行或小计唯一条件自动确定。打印行价已合计到 subtotal 时建议 included；未知/冲突必须选择确认，不能默默重复扣款。确认后 `priceCents` 永远是净行价，分账端无需处理负商品。
6. **校验层：** 对账分开检查 Σ净行价、购买数量合计（仅收据明确声明时）、subtotal + tax + charged tip、总税与税明细。payment 只作旁证，不能覆盖 total；added tip 继续排除在票面核对之外。匹配到一分钱以内与“识别正确”不是同一结论。
7. **复核层：** Receipt 编辑器增加 quantity / unit price / modifiers / discount 状态及相关源行；金额编辑字段明确是净行价。阻塞项为未确定净价、折扣语义、必要金额缺失；解决后才能确认。已有“有差额则解释原因”的路径保留，但不能仅填理由绕过未确定折扣。

DraftItem 沿用 `name / priceCents / sourceLine`，新增可选结构化 `details`（源行、坐标、quantity、unitPriceCents、taxCode、modifier、关联 ID、折扣语义与 reviewCodes）。confirmed ReceiptItem 的可选 `receiptDetails` 保存已复核元信息；所有数值校验和恢复贯穿 store/session/editor。旧 draft 无 details 仍兼容，并保留原 warnings。全局 confidence < 60 继续只是提示，不是单行金额的正确性阈值。

增强扫描只在金额缺失/无法对账或 confidence < 60 时考虑；比较当前默认分割与 single-column 等已安装引擎模式。重复加载、取消、重选、旧任务返回必须沿用现有 worker 生命周期保护。两次识别产生不同价格时显示冲突供确认，不挑一个恰好凑总额的结果。

## 交付顺序与验收

1. 建立三张小票的人工标注、原图基线和浏览器校正后基线；先分清 OCR 漏字与 parser 误解。
2. A：数据迁移、整数权重、按数量 UI、即时预览与结果核对，可独立验收。
3. B1：小票行分类/数量/附属项/折扣/税汇总与复核，可用真值文本独立测试。
4. B2：接入坐标与必要的增强扫描，以真实浏览器图像对比检验改善。

分账验收必须覆盖分/税/小费守恒、数量不足/超出、稳定余分、删除成员、刷新、返回 Receipt 修改、同名不同 ID。375px 和 1280px 下可用，不依赖颜色或 hover，控件可键盘操作。

小票的完美转录文本必须严格输出上述 11/6/15 个收费行及票面金额，不出现重复扣款、重复税或同名合并。真实 OCR 分别报告收费行 precision/recall、净行价匹配、名称/数量正确情况、税/总计识别、未解决项与人工改动数；既有 Line Thai 和合成测试不得回归。无法读出的内容必须保留为人工复核项，不通过把真值写回草稿伪装 OCR 成功。

最终数值目标在 Task 0 测完浏览器基线后列入验证记录供 review；本次不编造准确率、耗时提升或“支持所有小票”的承诺。图像校正与单行修正需独立记录，合计相等不能抵消两条金额一增一减的错误。
