# CheckMates：可核对的分账结果设计

日期：2026-09-29。状态：**设计已用于 `feat/split-explanation` 本地实现，等待用户验收后发布。** 基线：已上线 `main@8ce4d03`。

## 用户目标与范围

用户希望在分账时看到具体拆解或可视化，知道金额是怎么分出来的。截图位于 Result 页，因此本次优先增强 Result；Split 分配页的即时反馈作为下一小步。成功标准是用户能从菜品逐行算到个人应付，并理解税、小费及一分钱的归属。

这一请求将“解释分账”提到下一轮优先项。V2-B 菜品识别仍保留为待办，翻译仍是 V3；本设计不声称这些能力已经完成。

## 已确认的现状

- Result 的 `View breakdown` 目前仅显示 Items、Tax、Tip 三个总数，没有逐菜金额或计算依据。
- `splitBill` 已使用整数分和 BigInt 最大余数法：每道菜在被选中的成员间均分，税和总小费分别按个人菜品小计占比分配。
- 余数相同按 `bill.people` 中的稳定顺序分配；点选成员的先后不会改变结果。
- `SplitResult` 只保留最终金额，解释层需要从同一次分配中保留过程。

## 方案比较与选择

| 方案 | 优点 | 局限 |
| --- | --- | --- |
| 仅增加饼图或金额条 | 可快速看出谁付得多 | 仍无法解释具体菜品及税费，不能独立满足需求 |
| **个人卡片＋金额构成条＋逐菜明细** | 沿用现有界面，先看金额，再按需核对 | 展开区需要处理长名字、多菜和小屏幕 |
| 菜品到每个人的连线图 | 少量成员时直观 | 菜和人较多时线条拥挤，手机及读屏代价较高 |

建议第二种。图形帮助比较，精确金额和可展开的明细负责验算。

## 第一阶段：Result 页

1. 保留个人姓名、应付总额及现有卡片颜色；金额构成条用固定 Items / Tax / Tip 配色，所有人的长度使用相同最大总额尺度。
2. 展开个人卡片后依次显示：所分配菜品、个人菜品小计、税分配、小费分配、个人合计。
3. 每道菜显示完整行价、共享成员/人数和个人实际份额。行价已包含数量，不能因菜名带数量再次乘算。独享显示 `Only you`。分到零分的被选成员仍保留该行。
4. 税和小费显示 `总池 × (个人菜品小计 / 全单菜品小计)`，再显示向下取整后的基础金额与实际补到的余分。该比例使用整数分权重；百分比若展示必须标记约数，不能用于重新计算金额。
5. 小费沿用当前一个总池，即票面小费加用户新增小费。可以展示来源，但不能把两个来源重新各算一次而改变余分分配。
6. $0 小费明确显示 `No tip added`；全零账单显示零金额说明，不展示 `0 / 0`。极小图形区段不强制加宽，精确金额始终有文字。
7. 总结文案为 `Allocation difference $0.00`，只表示分配金额守恒，不能改为“收据已正确识别”或“票面已核实”。原有票面差异处理仍在 Receipt 页。

## 第二阶段：Split 页反馈与分享（另行评估）

- 点选某道菜的成员后，在该菜下显示每个被选成员的实际份额，复用相同分配函数。未分配时显示提示，不计算税或最终应付。
- 结果页增加“复制详细明细”，保留当前简版复制。详细版包含逐菜份额、税/小费依据和总额；不自动发送。
- 第一阶段 review 后再决定是否纳入同一版，避免原型探索扩大首批开发范围。

## 技术与验收约束

- 产品界面继续用英文；USD；非负安全整数分；分配规则完全兼容当前版本。
- 结果、明细、图形由当前 bill 的一次计算产生，不新增 localStorage 中的派生结果，不增加图表依赖。
- 375px 和 1280px 下无横向溢出；details 原生键盘可用，文字足以表达所有金额，不能依赖颜色或 hover。
- 返回修改金额、成员、分配后，结果与展开明细必须同步；删除的人不能残留在说明中。
- 验收关注金额一致性、零值、余分、同名不同 ID、大额及长文本；截图好看不能替代金额断言。
- 本次交付止于原型和计划；实施阶段先提供本地 demo，再由用户 review 后决定发布。
