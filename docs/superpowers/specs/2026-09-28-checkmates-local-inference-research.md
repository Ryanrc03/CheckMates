# CheckMates：本地 OCR 与英译中调研结果、下一步方案

日期：2026-09-28。状态：**调研与独立实验已完成，以下开发方案供 review，尚未接入应用。**

> 后续范围已更新：用户要求先完成每图动态校正，再完成菜品识别；翻译延至 V3。以下实测结果保留，下一步排期以[新版 V2 计划](2026-09-28-checkmates-v2-image-first-design.md)为准。主工作区应用代码已回到 MVP，本文描述的旧 V2 状态属于回退前背景。

本次聚焦两个问题：正确识别菜名和对应金额；一键把英文菜名及小票缩写翻译成简体中文。优先免费、在用户设备上推理，考虑照片倾斜。应用代码、生产部署均未在本轮修改。

## 1. 结论与建议

1. **OCR 不能只换引擎。** 图片校正、文字区域与价格的匹配、收费行分类需要一起处理。PaddleOCR 在本轮样本中读取文字的效果更好，但直接接现有解析器仍会错配金额；加入实验性的空间行匹配后才得到正确结果。
2. **先做倾斜校正，保留手动四角校正。** 合成的 7° 倾斜图，经自动估计 7.1° 并校正后，Tesseract 恢复正确识别。复杂小票做手动四角校正后，也恢复了税额和总额。自动找四角尚未验证。
3. **翻译采用“本地菜名词表＋有上下文的缩写展开＋受控的模型候选”。** 已测试的轻量英中模型对完整普通菜名有一定效果，但会误译菜系专名、缩写和否定词，不能直接作为默认可靠译文来源。
4. **先补测试，再接入。** 本轮只有两张基础图片和少量变体，全部在桌面 Chromium 上运行，不能宣称手机可用或真实小票准确率达标。

建议开发顺序：补充基准集 → OCR 校正与版面匹配 → 一键中文词表版本 → 验证更广覆盖的本地翻译 → 手机验收。结果可视化继续保留在原路线图中，本轮优先解决识别与翻译。

## 2. 当前应用的问题在哪里

当前 OCR 使用 Tesseract 和收费行分类、提取规则。预处理已有直角旋转、矩形裁剪和图片缩放，但没有任意小角度自动纠偏，也没有透视校正。

“准确识别菜品”至少分为四层：

| 层次 | 典型失败 | 需要的处理 |
| --- | --- | --- |
| 图片质量 | 斜拍、背景纹理、透视变形 | 纠偏、裁剪、四角校正 |
| 文字识别 | Lemonade 读成 Femonade | OCR 引擎与图像质量改进 |
| 版面关联 | 菜名和右侧价格成为不同文本框 | 按坐标、行高、列位置重建关联 |
| 业务语义 | 小计被当菜品，税率被当税额 | 收费区域和标签分类、金额核对 |

只识别数字无法区分价格、日期、数量、税率和付款记录。正确方向仍是识别文字及位置，再只把有用的菜品和收费金额写入账单。

当前应用尚无已实现的一键菜名翻译功能。翻译应作为独立展示层，保留英文原文，不改变菜品 ID、数量和算账金额。

## 3. 技术路线调研

| 候选 | 本地运行方式 | 优点 | 限制与当前判断 |
| --- | --- | --- | --- |
| Tesseract.js | 浏览器 Worker / WASM | 已接入，实测较快 | 对倾斜与背景干扰敏感；先补图像处理 |
| PaddleOCR 浏览器 SDK | Worker、ONNX、OpenCV | 返回文字多边形，适合后续版面匹配 | 需要引擎适配；本轮更慢，启动耗时有波动；作为高精度模式候选 |
| 本地菜名词表和缩写规则 | 普通前端数据与逻辑 | 无模型下载，确定的词条可稳定翻译 | 覆盖有限，必须显示未覆盖项，不能宣传任意菜名均可翻译 |
| Transformers.js + OPUS 英中模型 | 浏览器 WASM；框架也支持 WebGPU | 无按次推理费，跨浏览器方向可行 | 本轮模型质量未通过；下载较大，手机未测 |
| Chrome Translator API | 浏览器管理本地模型 | 可作为部分桌面环境的增强能力 | 官方文档目前限桌面 Chrome，不能覆盖手机；本轮未取得可用性和翻译质量结论 |

PaddleOCR 官方提供浏览器 SDK 和 Worker 路径，本次实测的是 **PP-OCRv5 mobile**，不是把文档中其他更新模型的能力当成已测结果。[官方浏览器说明](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/inference_deployment/cross_platform/browser.md)

Tesseract 官方明确指出，倾斜会影响行分割，纠偏和图像质量处理有价值。[图像质量指南](https://tesseract-ocr.github.io/tessdoc/ImproveQuality.html)

Transformers.js 支持在浏览器运行模型，但框架能执行翻译不等于某个模型适合小票菜名。[官方文档](https://huggingface.co/docs/transformers.js/en/index)；Chrome 原生方案仍需检查语言对、模型状态和用户激活条件。[Translator API 文档](https://developer.chrome.com/docs/ai/translator-api)

### 免费和 Vercel 的边界

这条路线不需要付费 OCR 或翻译 API，推理在用户浏览器执行。Vercel 承担网页和资源托管即可，不需要把模型放进服务端函数执行。

免费推理仍有首次下载、网络流量、设备内存、电量和等待时间成本。Vercel Hobby 有个人非商业用途和用量约束，不能理解为无限免费托管模型。[Vercel Hobby 说明](https://vercel.com/docs/plans/hobby)

生产接入前需要决定模型资源来源，固定版本、校验值与许可信息，并验证跨域加载和缓存。仅有本地推理不代表首次打开就能离线使用；完整离线能力尚未实现或验证。

## 4. OCR 独立实验结果

### 样本与方法

- 合成小票 `clear-diner.png`：3 个菜品，税 $2.01，总额 $26.41。
- 脱敏衍生图 `line-thai-cafe-2026-09-05-redacted.png`：6 个菜品行，价格依次为 $13.90、$7.90、$4.00、$25.80、$12.90、$8.00；小计 $72.50、税 $5.98、总额 $78.48。
- 对合成图生成 +7° 旋转变体，再用实验算法估计角度并校正。
- 对衍生图人工指定四角，执行透视变换。此操作同时改变背景范围和采样，不能把全部收益归因于透视校正本身。

衍生图经过生成式遮盖，不是未重绘的真实照片。两张基础图及其变体不能算成五张独立真实样本；实验规则也在这些图上调过，没有独立留出验收集。

### 实测对比

下表 Tesseract 使用现有解析输出；PaddleOCR 使用新增于独立实验的空间行匹配后输出。耗时仅是本机模型识别阶段，不含首次初始化、图片校正和整套交互流程，不是手机性能或 P95。

| 输入 | 引擎与解析方式 | 菜品结果 | 税 / 总额 | 待复核数 | 识别耗时 |

| 合成图 +7° | Tesseract + 现有解析 | 菜名误字，另把小计和税误收为菜品 | 均缺失 | 2 | 0.14 秒 |
| +7° 图自动纠偏后 | Tesseract + 现有解析 | 3 行正确 | $2.01 / $26.41 | 0 | 0.18 秒 |

| 合成正向图 | PaddleOCR + 空间行匹配 | 3 行正确 | $2.01 / $26.41 | 0 | 3.77 秒 |

这里的“行正确”指主要菜名及对应行金额，不代表所有换行备注、配料、数量语义均已完整验收。待复核少也不一定更正确：倾斜图上的 Tesseract 只有 2 项待复核，却已自动接纳错误收费项。

### 关键发现

**空间匹配是必须单独设计的部分。** PaddleOCR 的文字检测框可能把菜名和价格分别输出。直接接现有解析器时，原衍生图只得到 1 个菜品，还把 $72.50 错配为税。实验通过多边形估计文字方向、按行高与纵向位置分组、行内从左到右排序，才恢复正确关联。

这套实验规则不能直接套给所有引擎：对 Tesseract 原衍生图套用同样规则，反而把备注合并错、菜品从 6 行变成 5 行。因此需要各引擎独立适配，并验证多行菜名、配料和密集行距。

**小角度纠偏有效，但证据范围有限。** 自动估计得到 7.1°，纠正了人工施加的 7° 倾斜；尚未覆盖各种角度、折皱、阴影和真实手机透视。

**PaddleOCR 的启动与资源成本需要解决。** 两轮初始化分别约 6.1 秒与 151.9 秒，包含模型获取和运行时初始化，波动原因尚未定位。检测与识别模型归档合计约 21.5 MB，另需运行时资源；不能只看约 8 秒的识别耗时来承诺体验。

## 5. 英文菜名翻译独立实验结果

测试使用 Transformers.js 3.8.1、浏览器单线程 WASM、`Xenova/opus-mt-en-zh` q8，指定简体中文语言前缀。输入共 14 个原始短语，另加 4 个手动展开缩写的对照输入，共 18 次翻译。

| 输入 | 模型实际输出 | 评价或对照 |
| --- | --- | --- |
| Pineapple Fried Rice | 菠萝炸米 | 菜名应译为菠萝炒饭，词义不合适 |
| Fried Tofu (12) | 炸豆腐(12) | 可用，保留括号内容 |
| Milk Tea | 牛奶茶 | 能理解，但常用译法是奶茶 |
| Pad Thai | 泰语斜体 | 明显错误 |
| Pad Kra Pow | 帕德克拉波(PAD KRAPO) | 音译未提供足够菜品含义 |
| Brown Sugar Milk | 棕色糖牛奶 | 不自然，需要菜单词汇处理 |
| Chkn Fr Rice | 赖斯 | 手动展开 Chicken Fried Rice 后得到“鸡肉炒饭” |
| Veg Spr Roll | 紫色滚动 | 手动展开 Vegetable Spring Roll 后得到“蔬菜春卷” |
| Beef Ndl Soup | 牛肉汤 | 漏掉面；展开 Beef Noodle Soup 后得到“牛肉面汤” |
| w/o Onion | 洋葱 | 丢失否定；展开 Without Onion 后得到“没有洋葱” |
| No Peanuts | 无皮纳特 | 未正确翻译食材 |
| Extra Spicy | 额外辣椒 | 没有准确表达辣度 |
| GF Pad Thai | 泰语GF Pad | GF 本身有歧义，不能盲目展开 |
| BF Combo | 联邦信贷库 | 明显错误，BF 的含义仍需上下文 |

四个展开后的对照输入由实验人工提供，**没有证明自动缩写识别已经实现**。这组结果说明缩写处理值得做，也说明完整输入不一定能解决菜系专名问题。

本机首次初始化约 4.9 秒，单短语约 0.14–0.63 秒；此模型的 q8 编码器与合并解码器权重约 113.1 MB，另有 tokenizer 和运行时文件。首次下载速度不代表普通用户网络速度。跨域资源计时中出现的 0 字节不能作为没有下载的证据。[模型文件](https://huggingface.co/Xenova/opus-mt-en-zh/tree/main/onnx)

另一次请求 `num_beams=4` 的输出没有改变；当前测试版本源码仍有完整 beam search 支持的 TODO，不能把这次调用当成有效的四束搜索质量对比。

**判断：这个模型目前不通过作为默认菜名翻译器的质量门槛。** 不应为了展示“一键翻译”而把已知错误输出直接交给用户。可继续作为实验候选，换用其他本地候选时必须复用同一测试集。

Chrome 原生 Translator 的本轮测试仅确认接口暴露；进一步的语言对可用性检查因页面导航失败，未获得有效结果。因此暂不作“已可用”的结论。

## 6. 建议的产品行为和实现方向

### OCR：校正、识别、匹配、核对

1. 图片进入后检查方向与倾斜，提供预览；自动校正不可靠时允许用户拖动四角。避免裁掉底部税费。
2. 优先保留 Tesseract 快速路径；根据后续测试，把 PaddleOCR 做成按需下载的“重新精细识别”候选模式。先由用户主动选择，自动切换策略另行验证。
3. 统一保留文字内容、坐标、原始行和引擎来源，由各自适配器重建菜名、价格、数量、备注关系。
4. 按收费区域与标签区分菜品、税、小费、小计、总额、付款记录和无关信息。未知财务行保留复核，不能直接丢弃。
5. 用小计与总额检查发现矛盾，不通过凑总额、补价格或猜小数点来“修正”识别结果。
6. 点击某行可查看原图对应区域；用户编辑后，迟到的识别结果不能覆盖手动修改。

### 翻译：一键展示中文，同时保留英文

建议在菜品确认页放置明确的“一键翻译为中文”入口；按当前界面语言可显示为 `Translate to Chinese`。点击后处理当前所有菜品，并逐项显示成功、未覆盖或待确认状态。翻译不应依赖结果可视化模块先完成。

处理顺序建议如下：

| 步骤 | 行为 |
| --- | --- |
| 保留原文 | 始终保存原始英文、用户编辑后的英文，以及独立中文显示字段 |
| 菜名与短语匹配 | 优先使用经过检查的完整菜名、饮品和修饰词词表；不做任意子串替换 |
| 缩写处理 | 根据词边界、邻近食材和菜型展开 CHKN、NDL、FR RICE 等候选；显示可检查的展开结果 |
| 歧义处理 | GF、BF 等不确定缩写保留原文；可采用用户确认的餐厅专属映射，不建立无条件全局替换 |
| 关键语义保护 | `no`、`without`、`w/o`、`extra` 和数量通过确定规则单独处理，不允许否定丢失 |
| 未覆盖输入 | 首版保留英文并标为未翻译；后续只有通过质量验收的本地模型才能提供参考译文 |
| 缓存与更新 | 按原文、规则版本、模型版本缓存；英文修改后旧译文失效 |

第一版词表可以覆盖常见美式餐饮、饮品和常见亚洲菜名，但需要声明覆盖范围，并单独报告词表命中率。遇到 `Pad Kra Pow` 等未标明肉类的名称，译文不能自行添加“鸡肉”或“牛肉”。

“一键”表示一次操作处理整张账单，不表示遇到任意未知菜名都强行生成中文。若希望所有未知菜名都有自动参考译文，仍需继续验证更广覆盖的本地模型，当前实验不足以选定生产模型。

## 7. 下一步分阶段计划

### 阶段 A：冻结测试集和对照方法

交付物：标注规范、样本清单、OCR 对比报告、翻译人工评价表。

- OCR 延续原计划最低要求：至少 10 张未重绘实拍、至少 100 条收费行；6 张用于开发，4 张不同版式留出验收。同一小票的旋转变体不能跨开发集和验收集。
- 覆盖正向、小角度倾斜、透视、长小票、多行菜名、重复价格、数量、税率和付款区。图片不足时只报告已测范围。
- 翻译建立至少 50 个真实菜单或小票短语，包含完整菜名、菜系专名、缩写、否定和歧义；至少 20 个保留为未参与词表调试的验收样本。
- 记录菜名与价格配对、漏项、错收费用、备注归属、待复核数，以及用户修正次数；翻译分别统计词表覆盖率、已翻译项正确率和总体可用覆盖率。

### 阶段 B：OCR 改进

交付物：自动小角度纠偏、手动四角预览、按引擎适配的版面匹配、原图定位复核。

- 先验证 Tesseract 加预处理的收益，再决定 PaddleOCR 是否值得作为可选模式接入。
- 给多行菜名、配料、价格列和税费归属建立回归案例，防止空间合并引入新错误。
- 把模型初始化、图片预处理、识别和解析分别计时，定位 PaddleOCR 初始化波动。
- 两个引擎结果冲突时保留可见差异，不能凭引擎置信度自动替换用户确认的金额。

### 阶段 C：一键中文功能

交付物：明显的批量翻译按钮、中英对照、已审核词表、缩写规则、未知项状态和用户修正缓存。

- 先完成无需模型下载的词表版本，让一键入口真正可用。
- 在同一留出集上测试其他可在浏览器运行的英中候选及可用的桌面原生 Translator；记录许可证、模型大小、质量和延迟。
- 当前 OPUS 候选保留在实验区；未通过验收前不默认接入。
- 不把 OCR 识别出的整张小票送入翻译，也不让译文反过来覆盖原始账单数据。

### 阶段 D：模型资源与手机验收

交付物：按需加载、缓存版本管理、下载进度与取消、失败恢复、实际手机测试记录。

- 在实际 iPhone Safari 和 Android Chrome 上验证，记录设备型号、浏览器版本、冷启动、缓存命中、单张耗时和内存问题。
- OCR 与翻译任务排队，避免多个大模型同时启动；取消后释放 Worker 和可释放资源。
- 验证刷新后缓存、模型资源不可达、下载中断、后台切换、低内存和用户编辑中的竞态。
- 验证照片、菜名和识别文本只在本地处理；模型下载请求不包含账单内容。
- 完成设备测试后再设置性能承诺，随后制作预览版本 review，再决定发布。

### 拟定验收门槛

以下是后续目标，不是本轮已取得成绩：

| 项目 | 建议验收方式 |
| --- | --- |
| 收费提取 | 延续原计划：留出集自动收费项用途与金额均正确的精确率 ≥98%，真实收费行精确金额召回率 ≥90%；同时报告分子、分母和菜名匹配质量 |
| 菜名与备注 | 单独人工检查菜名是否可辨认、是否绑定正确价格；数量、换行备注和配料不得静默串到其他菜品 |
| 干扰数字 | 固定干扰集的日期、电话、税率、建议小费和付款金额误入收费字段数为 0 |
| 翻译质量 | 已输出中文的条目中，人工判断核心含义正确比例目标 ≥95%；同时披露未翻译比例，不能靠大量跳过虚报覆盖效果 |
| 关键翻译语义 | 验收集中的否定、数量、食材和未提供信息的臆测错误数为 0；有歧义时明确保留原文 |
| 性能与兼容 | 必须有真实 iOS / Android 记录；Tesseract 快速路径继续与同机基线比较，PaddleOCR 候选单独评估，不沿用快速路径承诺 |
| 可恢复性 | 模型不可用、取消或翻译失败时，仍可手动完成账单；不丢失已编辑数据 |
