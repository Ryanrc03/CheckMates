# CheckMates V2 迭代设计与路线图

> 2026-09-28 状态更新：本文件作为历史设计保留，执行顺序已被[动态图片校正优先的新版计划](2026-09-28-checkmates-v2-image-first-design.md)取代。未 review 的 V2 应用改动已在主工作区回退至 MVP；翻译延至 V3，结果可视化暂缓。下文的旧排期不再作为执行授权。

日期：2026-09-27。状态：**供评审的计划草案，尚未实现**。基线：`main@cc06071`。

## 1. 用户目标与范围

用户已明确：OCR 要“只识别菜品、税、小费等有用金额，过滤其他数字”。这不是“只补填缺失金额”的功能。本次三个目标是：减少整理识别结果的时间；让用户看懂每个人为何付这个金额；方便中文使用者快速理解英文菜名。

翻译方向暂定 **英文 → 简体中文，原文与译文并列**。这是规划假设，尚未由用户指定语言范围。V2 继续使用英文主界面、USD、无账户的五步分账流程。

| 迭代 | 交付结果 | 优先级 | 依赖 | 计划 |
| --- | --- | --- | --- | --- |
| V2.1 OCR | 正确区分收费金额、参考金额、无关数字；疑似行集中复核 | P0 | MVP | [OCR 计划](../plans/2026-09-27-checkmates-v2-ocr.md) |
| V2.2 结果核对 | 每人金额构成图、逐菜分摊、税费公式及余分解释 | P0 | MVP 的账单结构 | [结果计划](../plans/2026-09-27-checkmates-v2-results.md) |
| V2.3 菜品翻译 | 按需中英对照，缓存，失败可继续分账 | P1 | 菜品 ID 与原文稳定；详细分享接入 V2.2 | [翻译计划](../plans/2026-09-27-checkmates-v2-translation.md) |

推荐按表中顺序发布。结果模块不依赖新的 OCR 引擎，可以独立实现；翻译不能成为录入、分配或计算的前置条件。每一阶段都有独立发布与回退点，不需要等三个模块全部完成。

本文的中文按钮/文案描述用于说明需求；除中文菜名外，实际界面继续使用英文，例如 `Needs review`、`Ignored information` 和 `Show Chinese names`。

## 2. 当前实现与需要解决的问题

- `src/lib/ocr/worker.ts` 只请求纯文本及整体置信度；`parseReceipt.ts` 逐行使用正则表达式，容易把背景噪声变成缺价菜品。
- 解析代码依靠关键词过滤，尚没有稳定的“行用途”数据模型。`Tax ID`、`Total savings`、小费建议与实际已收小费，需要结合标签和区域判断。
- `ResultStep` 仅有 Items / Tax / Tip 汇总。`splitBill` 计算正确，但返回值没有保留逐菜分配和余分归属，UI 无法解释过程。
- 目前没有翻译依赖。账单名称直接用于编辑、归属及分享；若直接替换名称，会破坏用户对原票的核对。
- 公开的 Line Thai 图片是经过生成式遮盖的衍生样本，文字像素可能发生变化。它可以继续作回归样本，但不能单独证明真实照片准确率。V2 要把未重绘的真实照片、遮盖衍生样本与排版合成样本分开统计。

## 3. 全局约束

1. 金额仍为非负安全整数分；分账采用稳定参与者顺序和最大余数法。任何图表、翻译、OCR 提示都不能改变算账规则。
2. 照片与识别默认在浏览器内处理，不上传小票。V2 默认不新增云端 OCR 或翻译接口。
3. OCR 的引擎置信度仅为复核信号，不代表金额正确概率；不为了凑齐总额而猜价格、移动小数点或补小费。
4. 翻译只增加展示信息，不能覆盖菜品原文、修改价格或把金额送入翻译模型。
5. 保留取消、超时、重试、手动录入和刷新恢复。新功能失败不阻止手动完成账单。
6. 模型和运行时按需加载，记录固定版本、模型 revision、文件大小、校验值和许可证；不直接跟踪 `latest` 或模型 `main`。
7. 手机优先：375px 可用，按钮可触达，键盘与读屏可操作；信息不能仅由颜色或 hover 提供。
8. `bitesplit-session` 保留作为兼容存储键。OCR 扩展后写入版本 2，并迁移版本 1；不清空原有账单。
9. 修改 Next.js 代码前先阅读本仓库 `node_modules/next/dist/docs/` 中相应指南，不能直接照搬不同版本的示例。

## 4. V2.1：识别“这是什么钱”

### 4.1 提取规则

先 OCR 读取上下文，再按标签、版面位置、相邻行和金额格式决定哪些数据进入账单。整张图不能只保留数字字符，否则无法区分日期、税率和价格。

| 类型 | 示例 | 处理 |
| --- | --- | --- |
| 菜品行总价 | `Pad Thai ×2 $25.80` | 录入 2580 分；不再次乘以 2 |
| 数量/份量/单价 | `×2`、`Tofu (12)`、`$12.90 each` | 不当作新增收费行；保留用于核对 |
| 税额 | `Tax (8.25%) $5.98` | 录入 598 分；8.25% 仅为参考 |
| 已收小费 | `Gratuity (18%) $4.00` | 标签和区域证明是已收费用时，录入 400 分 |
| 建议小费 | `Suggested tip 18% $4.39` | 不计入已收小费 |
| 小计与总计 | `Subtotal`、`Grand total` | 只用于对账，不成为菜品 |
| 付款记录 | `Visa $78.48`、cash/change/tender | 不重复加到总额中 |
| 元数据 | 日期、电话、桌号、订单号、卡尾号、Tax ID | 不进入菜品或费用字段 |
| 折扣/服务费等未知收费 | `Discount -1.00`、`Svc Chg 2.00` | 独立标为财务疑点，要求人工处理说明，不能悄悄丢掉或自动当小费 |
| 金额不清楚的疑似菜品 | `Soup 8.0`、缺价 `Salad` | 放入显著的“待确认”区域；可补价加入、合并备注或排除 |

只把有充分证据的项目放入默认表单。疑似菜品和财务疑点必须可见、可恢复；明确的电话/日期等放入折叠的“已忽略信息”。不能靠隐藏所有困难行来提高精确率。

V2.1 不引入负金额账单模型或复杂优惠分摊。发现折扣/服务费时，用户必须按原票修正受影响的现有金额并填写处理说明；无可正确表达的修正方式时，明确保留为未解决，而不是显示对账成功。

### 4.2 技术方向

保留 Tesseract.js 6.0.1，先扩展 `blocks` 输出，转换成行/词及坐标，再建立纯函数分类和提取层。旧纯文本入口保留为兼容路径。新增简单手动裁剪，减少桌面背景干扰；自动透视校正和换 OCR 引擎不列为首轮必做项。

裁剪按已旋转的预览坐标进行，裁剪后再缩放，识别原始收费内容。重新识别仍明确提示将替换当前编辑，用户已排除的行不能被迟到结果复活。

### 4.3 验收与基线

- 建立至少 10 张未重绘的英文餐厅实拍、累计至少 100 条人工标注收费行；6 张用于调规则、4 张不同版式留作验收。图片不足时保留“实验性”标识，不宣称真实准确率已达标。
- 每张记录输入类别、是否裁剪、原始 OCR、自动接纳项、待复核项、被忽略项、修正次数与最终账单。公开素材按实际使用授权处理；原始交易标识不能进入 Git 历史或报告。
- 以下是**拟定门槛，不是已取得结果**：留出实拍上的自动收费项“用途和金额均正确”精确率 ≥98%，真实收费行精确金额召回率 ≥90%。同时报告分子/分母、菜品名质量、税/小费字段和待复核率，避免小样本百分比误导。
- 固定干扰集里的电话、日期、卡号、数量、税率、建议小费和付款金额，误入可收费字段数为 0。六条相同菜价也不能按“金额相同”误去重。
- 在同一设备、同一语料上对比 MVP；P95 总识别时间不超过基线 1.5 倍，原有 120 秒上限和可恢复错误保留。

## 5. V2.2：让结果可以逐项验算

### 5.1 展示结构

结果页顶部保留账单总额与“分配合计 / 差额”。下方每人展示横向堆叠条：菜品、税、小费，共用同一金额刻度，便于看出谁支付较多。始终显示准确数字和图例；零金额仍有文字，不用图形面积代表精度。

展开个人卡片后显示：每道菜原价、共享人数、本人的份额和余分说明；税/小费按个人菜品小计占比计算的公式；最后显示 `菜品 + 税 + 小费 = 应付`。另有全单“费用如何分摊”，解释稳定顺序和最大余数法。

不首选饼图：横条在窄屏更易比较，也更适合读出金额构成。图形可用 CSS/SVG 实现，不为这一个图新增大型图表依赖。

### 5.2 固定验算案例

账单：A/B 共吃一份 1001 分菜品，B 独享另一份 500 分；税 151 分，小费 302 分。

| 项目 | A | B |
| --- | ---: | ---: |
| 共享菜基础份额 500 分，余 1 分按参与者顺序给 A | 501 | 500 |
| B 独享菜 | 0 | 500 |
| 菜品小计 | 501 | 1000 |
| 税：先取整数分 `[50,100]`，余 1 分给余数更大的 B | 50 | 101 |
| 小费：先取整数分 `[100,201]`，余 1 分给余数更大的 A | 101 | 201 |
| 应付 | **652** | **1302** |

账单总额与分配总额均为 1954 分。UI 可以显示近似百分比，但计算必须使用精确整数权重，不能从四舍五入后的百分比反算金额。

### 5.3 单一计算来源

把当前计算函数扩展为“计算结果 + 分配过程”。`splitBill` 与详情页共享同一次分配逻辑；UI 不自行重新计算。对账状态分开显示：**分摊守恒**仅证明每分钱已分配；**与小票一致**需要已识别的票面总额和复核记录。票面总额缺失时显示“未能核对票面总额”，不能显示完全核对通过。

## 6. V2.3：菜品快速翻译

### 6.1 使用流程

确认菜品后提供“显示中文菜名”，并支持单项翻译。在核对、分配、结果明细中显示 `Pineapple Fried Rice` / `菠萝炒饭`。原文始终可见；关闭译文立即恢复纯原文。复制结果默认原文，用户可选择双语明细。

只处理菜品名和明确的修饰词（如 `No Onion`），不翻译人名、金额、地址、整张 OCR 原文或任意页面 DOM。菜名未改动时重复访问直接读缓存；修改原文立即撤销旧译文；同名菜共享缓存，但条目仍按 ID 区分。

### 6.2 方案比较与推荐

| 方案 | 优点 | 代价 | V2 定位 |
| --- | --- | --- | --- |
| 本地人工词表 | 很快、体积小、可校正常见菜名 | 覆盖有限，不能假装是通用翻译 | 首层精确命中 |
| Chrome Translator API | 浏览器内翻译、按语言包管理 | 官方当前仅支持桌面；不可在 Web Worker 内调用 | 桌面增强适配器 |
| Transformers.js + 英中 ONNX | 可由产品控制，浏览器内推理 | 下载、内存、手机耗时必须实测 | 先做可行性验证，再作为按需模型方案 |
| 服务端翻译 API | 可覆盖更多弱设备，下载小 | 菜名离开设备、API 成本和服务端限流 | 本轮不默认启用，若本地方案失败再单独决策 |

推荐“词表/缓存优先 + 可用时浏览器内置翻译 + 按需本地模型”。用户点翻译后才准备模型；OCR 忙时模型翻译排队，纯词表/缓存命中仍可立即展示。OCR 开始前暂停翻译并释放应用持有的模型实例，避免同时初始化或推理；浏览器内置模型的实际缓存由浏览器管理。原生下载需要用户激活，排队后若激活已失效，提供继续按钮重新触发。

候选为 `Xenova/opus-mt-en-zh`，仅是待测候选。其量化 encoder 约 52.9 MB、merged decoder 约 60.2 MB；这两项合计约 113.1 MB，尚未包含 tokenizer、runtime 或不同加载路径的其他文件。不能承诺首访“秒开”，也不能把整个模型仓库大小当单次下载量。候选原模型标注 Apache-2.0，发布前还要核查具体 ONNX 产物及各依赖的许可。

### 6.3 技术验证门槛

- 使用 50 个独立人工标注菜名，含缩写、泰/日菜音译和否定修饰词；通用可理解译法 ≥90%。错把 `No Onion` 翻为含洋葱或改变数量的样例为 0，否则改为保留原文或词表纠正。
- 以一台桌面 Chrome、一台实际 Android Chrome、一台实际 iPhone Safari 为测试矩阵，分别记录可用性；模拟手机宽度不能替代设备验证。
- 拟定预算：模型热态 10 道菜 P95 ≤3 秒；冷态在固定 20 Mbps 网络条件下 ≤90 秒或进入可恢复错误；按钮在 100 ms 内显示状态；用户取消后 1 秒内恢复可操作状态。记录真实请求字节数和可获得的内存指标，不伪造浏览器无法测得的峰值。
- 不达标的平台只保留词表/原文路径并标明能力；若手机通用翻译无法达标，不把 V2.3 标为全面完成，先交付测量报告再决定云端方案。

## 7. 发布与评审边界

本次交付仅为设计与实施计划，不修改运行中的站点。实施时每个迭代先跑受影响单测、真实浏览器流程和生产构建，再做 Vercel 预览；验收后才更新生产。现有 Vercel 项目尚未配置 Git 自动部署，发布步骤不能假定 `git push` 会自动上线。

后续评审重点：英文到简中的假设；上述质量与性能门槛；未知折扣/服务费继续人工处理；本地翻译不达标后是否允许选择云端服务。
