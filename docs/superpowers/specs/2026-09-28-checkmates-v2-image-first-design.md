## 2. “动态校正”具体是什么意思

**每一张输入照片独立分析、独立估计、独立生成变换。** 不复用上一张照片的角度或四角，不固定旋转 7°，不让用户先遇到坏的 OCR 结果才发现有校正入口。

需要分开处理两种变形：

| 情况 | 表现 | 对应处理 |
| --- | --- | --- |
| 平面内旋转 | 整张小票斜着，文字行基本互相平行 | 检测文字行方向，估计当前照片角度，旋转纠偏 |
| 透视变形 | 斜着对准桌面拍摄，小票上窄下宽或左右高度不同 | 检测小票边界，估计四角，再变换成正视矩形 |

单纯旋转无法修复透视。四角校正也无法解决严重折皱、弯曲、遮挡或已经模糊掉的文字；这些情况需要提示重拍或手动录入。

### 用户看到的流程

1. 拍照或选图后，立即进入“调整照片”阶段，显示原图并开始自动分析。
2. 完成后显示建议的边界与校正预览，默认使用本张照片计算出的结果。
3. 用户可直接选择“使用此照片并识别”，也可拖动四角、旋转 90°、微调角度、恢复原图。
4. 自动检测不可靠时，明确提示“请调整小票四角”，仍允许保留原图继续；不把不确定结果伪装成校正成功。
5. 确认后，现有 OCR 读取校正后的图像，再进入菜品确认页。

这一步对**每张新照片**执行，但不要求每次手动拖四角。正常照片可接受自动结果直接继续。手动录入和内置 demo 沿用原入口。

更换照片必须重置旧角度、四角、预览与异步任务；回到同一张照片调整时保留该照片的编辑。已经修改菜品后重新识别，需要继续保留替换草稿的提示。

## 3. 技术选择与理由

| 路线 | 优点 | 代价 | 决策 |
| --- | --- | --- | --- |
| 只增加手动旋转、四角 | 实现较直接，结果可控 | 每张都要用户操作，未满足动态处理要求 | 作为备用操作，不作为主流程 |
| 自动角度与边界分析＋人工可修正预览 | 每图独立处理；失败可解释和恢复；与现有 OCR 解耦 | 要验证边界和角度可信度，需要手机测试 | **推荐作为 V2 第一阶段** |
| 先更换 OCR 或使用大模型处理整图 | 可能改善文字读取 | 下载与性能成本更高，仍不能保证照片区域和金额关联正确 | 第一阶段不采用，识别阶段再基于数据选择 |

图片校正不以“更换 OCR 引擎”为前提。优先用浏览器 Canvas、Worker 和传统图像分析实现；如透视和轮廓处理确需引入 OpenCV.js，先验证包体、初始化和手机内存，再作为明确依赖提交 review，不把全部 OCR 模型顺带引入。

## 4. 图片处理设计

### 4.1 每图执行的顺序

1. **解码与方向归一化**：沿用 JPEG、PNG、WebP、15 MiB 输入限制；处理 EXIF 方向，保留 90° 方向纠正入口。
2. **生成分析缩略图**：最长边不超过 1024 像素，仅用于检测；不反复修改原图。
3. **检测小票候选边界**：利用边缘、轮廓、凸四边形与内部文字分布筛选；背景复杂、白纸贴白桌或票边缺失时返回不确定结果。
4. **估计文字行倾斜**：在候选区域内估计主文字方向。方向归一化后的残余倾斜搜索覆盖 -45° 到 +45°；不能因为实验只测过 7° 就只支持固定角度。
5. **生成变换建议**：结合边界和文字方向，避免先透视后又重复应用同一个旋转角。记录一个可追溯的最终变换，而不是不断旋转已经处理过的图片。
6. **预览与用户调整**：四角和角度都绑定当前照片；变换从未损坏的源图重算。预览和最终导出使用同一组参数。
7. **确认后导出**：输出不超过 600 万像素的图像给 OCR，填充边缘为空白，释放不再使用的图像和 Worker 资源。

自动检测不出纸张完整轮廓时，仍可建议全图纠偏；不能为了得到四边形而把最后一行菜品、税、小费或总额裁掉。自动角度不可靠时保持原图状态并提示调整，不应用猜测角度。

### 4.2 坐标和状态约束

- 原图、预览、导出图的坐标变换必须可换算。四角用相对源图的归一化坐标保存，避免手机屏幕缩放导致定位偏移。
- 四角保持一致顺序，禁止交叉、退化、越界和接近零面积的四边形；无效操作提示修正，不能生成空图或畸形图。
- 四角可触摸拖动，也能通过键盘选择与移动，状态不能只用颜色表达。
- 每次选图或重新分析产生新的任务 ID；旧任务完成后不能改变新照片或已确认结果。
- 撤销、恢复原图、取消处理、重新选图都是明确状态，不清空已有账单。
- 用户选择原图继续也算完成了校正阶段的明确决策，不把手动录入和失败恢复锁死。

### 4.3 对现有代码的影响范围

| 模块 | 拟定职责 |
| --- | --- |
| `src/lib/ocr/preprocess.ts` | 保留文件校验与导出入口，调用独立的图像校正模块 |
| 新增 `src/lib/receipt-image/` | 几何变换、边界检测、倾斜估计、Worker 通信；不包含金额解析 |
| 新增 `src/components/receipt/photo-adjustment.tsx` | 原图、四角、校正预览、接受与恢复操作 |
| `src/components/bill-wizard.tsx` | 将“上传即 OCR”拆为“上传 → 校正 → 确认后 OCR”，管理取消和照片生命周期 |
| `src/components/receipt/receipt-step.tsx` | 提供回到照片调整的入口，保护用户已编辑的菜品 |

阶段一尽量将图片编辑状态保留在当前照片会话中，不为此整体引入旧 V2 的存储迁移和收费复核界面。刷新后不能恢复原图时，沿用 MVP 的重新附图机制。

## 5. 分阶段交付与 review 点

### V2-A：先交付动态图片校正

这是下一次唯一优先开发的交付物。第一阶段仍使用 MVP 的 OCR 和解析逻辑，便于确认改善来自图片处理。

- [ ] 从 MVP 建立独立开发分支；先建立多角度、透视和失败输入的测试样本与预期。
- [ ] 实现每图独立的角度检测和旋转纠偏，验证正负角度、零角度、90° 方向调整和 EXIF。
- [ ] 实现四角透视变换、自动边界建议及不可靠时的手动操作。
- [ ] 接入上传后的首个照片处理阶段，显示校正前后预览和“使用此照片并识别”。
- [ ] 验证取消、更换照片、恢复原图、无效四角、重新识别与用户编辑保护。
- [ ] 提供本地 demo、同图前后结果和真实手机记录，交给用户 review；不同时合入新菜品解析器。

这里允许“自动分析失败 → 人工调整”，但不允许“每张始终使用同一个角度”或“完全跳过自动分析”。自动边界检测和文字角度分析的成功率必须分别报告。

### V2-B：再完成菜品与金额准确识别

在 V2-A review 后推进，以上一阶段确认的图像为输入。

- [ ] 获取文字及坐标，保留原始证据，分别处理菜名、数量、配料、行总价。
- [ ] 建立引擎对应的行列匹配，验证多行菜名、价格列、紧密行距和重复价格，避免把备注挂到下一道菜。
- [ ] 分类菜品、税、已收小费、小计、总额和付款记录；电话、日期、卡号、税率、建议小费不得成为收费项。
- [ ] 给不确定的收费项提供简洁、可操作的复核方式，并能定位原图；不为了凑平总额猜价格。
- [ ] 在相同实拍上比较“校正后 Tesseract”与“校正后 PaddleOCR＋适配器”。只有实际增益值得下载与性能成本时才提出引擎切换。
- [ ] 单独展示识别对比、人工修正次数和剩余失败样本，再交用户 review。

旧 V2 分支可以参考测试思路和个别函数，但每项复用都要成为独立、可 review 的新差异，不能通过一次合并恢复整版未审核改动。

## 6. 验收与证据

### 图片校正阶段

- 使用独立原图生成 -30°、-15°、-7°、0°、+7°、+15°、+30° 变体，并另测未用于调参的非整数角度；支持不同图片尺寸和四种 EXIF / 用户方向组合。角度来自输入分析，不传入生成时的已知角度。
- 合成平面旋转样本校正后的文字残余倾角目标 ≤1°；报告每张误差及失败数，不用平均值掩盖方向反转。
- 透视样本分别检验自动四角与手动四角；检查边界裁切、文字可读性和收费区域完整性，不把“图片变成矩形”当作通过。
- 至少加入白纸白背景、桌面复杂纹理、票边缺失、强阴影、弯曲和模糊案例；不可靠检测应进入可恢复状态。严重不可读图片允许提示重拍。
- 顺序上传两张不同角度照片，第一张慢任务不得影响第二张；校正预览必须与实际 OCR 输入一致。
- 在真实 iPhone Safari 与 Android Chrome 上试拍、拖角和取消，记录分析、预览、导出各自耗时及内存异常。桌面模拟视口不能替代手机验收。

### 菜品识别阶段

- 至少 10 张未重绘的真实小票、累计至少 100 条收费行；6 张开发、4 张不同版式留出。相同原图的变体不能跨开发与验收集。
- 留出集自动收费项“用途与金额均正确”精确率目标 ≥98%，真实收费行精确金额召回率目标 ≥90%；同时人工评价菜名、价格配对和备注归属。
- 固定干扰集中的非收费数字误入收费项数为 0。数量 2 对应的行总价不能再次乘 2；两个同价菜品不能被误去重。
- 单独报告菜名仍有错字、税费缺失、待复核项和人工修正次数。总额碰巧一致不代表识别正确。
- 这些均为后续目标。现有两张基础实验图片不足以证明达标，图片校正也不能保证所有 OCR 错误消失。
